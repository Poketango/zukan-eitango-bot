# 動画制作の指示書（ポケモン雑学チャンネル）
プロデューサー（ユーザー）がこれまでに出した、毎回守る指示のまとめ。台本を書くとき・動画を直すときは必ず全部確認する。

## 話題・台本
- 有名な話（ポケモン好きなら知っている定番、まとめサイトで何度も出る話）は使わない。対戦の有名なエピソードも同じ（例 2014年の世界大会で優勝したチームのパチリスは有名すぎてNG）。有名だと思った話は、確認を取らずに自分の判断で外してよい。
- 同じ内容のショートは二度と上げない。
- 見出しや札の言葉は、それだけで意味が伝わるものにする（×「ピカチュウの名前のタンパク質」→〇「ピカチュウにちなんだ目のタンパク質」）。
- 知らない固有名詞は即座に理解できないので、出てきたら必ず説明する（例 アボミナブル・スノーマン＝ヒマラヤの雪男イエティの英語での呼び名）。
- 会話は自然に。答えとして不自然な返事（質問ではないのに「正解」と返す等）や、言うまでもない確認（「ほんとに6文字なのだ」）は入れない。
- 反応は内容に合わせる。強引な語呂合わせは「自然につながる」ではなく「ちょっと強引で面白い」と言う。
- 有名な都市伝説がある話題（ゴースト→ゲンガーの体重増加とピクシー説など）は「ふしぎね」で流さず、その説に触れる（公式設定でないことも言う）。
- ただの直訳（海外版の町の名前が英語の色の名前、など）は雑学にならないので扱わない。
- ずんだもんが推測したら、ひまりはその推測にちゃんと答える（例 マサラ＝カレーのスパイス？→関係ないと言ってから正解を言う。「おしい」など意味の通らない返しはしない）。

- サムネイルと題名には、6つのうちいちばん惹きのある話題（ひと目で伝わって意外なもの）を選ぶ（例 脳の研究より、国のお金になったピカチュウの硬貨のほうが惹きがある）。

## 画像
- 古いゲームや機械（ポケモンスタジアム、ポケットピカチュウなど）は、知らない人が多いので、どんな物かを画像（物の写真・箱・ゲーム画面）と文章の両方で必ず説明する。コモンズで見つからなければ探し方を変え、Serebii・コインの図鑑サイトなどの画像を web:URL で使う（^ で代わりの画像も書く。Bulbagarden は Actions から取れないので下の方法でリポジトリに入れる）。
- 説明は言葉より図示。ほぼ全部の行に、中身が目で見てわかる画像を出す（指示された場所以外にも入れる）。
- 文字だけのカード（ふきだし）は普通の文字と認知負荷が変わらないので使わない（word: は使わない）。
- 図の注目してほしい場所は赤い丸で囲む（@mark=x,y,w,h@label=札）。位置は実際に画像を見て決める。
- 話に出た物そのものの画像を出す（スパイスのマサラの話ならガラムマサラの写真、町の話なら町の地図 kanto: など。色だけ出すのはNG）。
- 答えを言う前の質問の場面で、答えの画像を先に出さない（「網膜はどこ？」の場面で網膜に印をつけた図＝fig:eye ではなく fig:eye0、「最初のポケふたはどこ？」の場面で鹿児島の地図、などはNG）。
- 棒グラフは誤解を生まないよう正しく作る（自動で0からの目盛りがつく。unit=kg のように単位を必ずつける。1本だけの棒グラフは作らない）。
- 画像は出したあと動かさない（揺らす・ゆっくりズームはしない）。
- 同じ画像を、切り替えるように連続して出し直さない（同じ画像が続くときは札だけ変わる。似た図を何度も出さない）。
- 文字（札など）が枠からはみ出したり、枠ぎりぎりになったりしないようにする（札は16字以内）。
- 外国語の文字（韓国語など）は、表示できるフォントがないので使わない。
- 著作権に神経質になりすぎなくてよい。大手の解説チャンネルと同じように、ゲーム画面やアニメの画像も使ってよい（ゲームの町の話なら、その町のゲーム画面を出す）。Bulbagarden Archives（archives.bulbagarden.net）の画像は GitHub Actions からは取れない（403）ので、内蔵ブラウザで archives.bulbagarden.net のページを開き、ページ内のJSで画像を fetch してまとめてダウンロードさせ、device_stage_files で取り込んで assets/img/<種類>_<名前>.png としてリポジトリに入れて使う（例 town:masara）。
- 字幕の数字と単位の色分けは単語の途中で切らない（「1トン」の「1ト」だけ赤、はNG）。

## 読み上げ
- 字幕（t）を直したら、読み上げ（say）も必ず同じ内容に直す。say があると字幕ではなく say が読まれるので、t だけ直すと古いせりふが流れる（「きれいにつながるでしょ」が残った失敗）。
- 数字と単位の読みに注意する（「十文字」を「じゅうもんじ」と読む、など）。自動で直せないものは say にひらがなで書く。
- ひまりは落ち着いた解説役なので、抑揚を一定にする。

## 編集
- テンポが同じだと飽きるので変化をつける。フォント・アイキャッチ・画像の種類を多様にする。
- 字幕は全体のバランスを見て改行し、句読点だけの行や、単語・数字の途中での改行を作らない。
- エンディングのBGMは本編と別の曲にして区切りをつける（bgm_sections の ED_PATTERN）。

## 終わりの画面
- 動画の最後に約20秒の終わりの画面（前回の動画・おすすめの動画の枠、チャンネル登録の丸）を入れる。YouTube の終了画面の要素をこの枠に重ねる。

## X（@zukan_eitango）用の雑学カード
- 台本の各話題に "x" を必ず書く。台本を push すると、Actions の「x-cards」が x/NNNN_k.png（1080x1350の縦長カード）と x/NNNN_posts.json を自動で作り、毎日のXの投稿に使われる。
- 形式：{"head": "画像の上に大きく出す言い切りの一文（20〜30字。数字や具体名を入れる。カタカナ語の途中で改行されない長さに）", "img": ["art:25|札"]（1〜2枚。比べるなら bars:。web: や commons: も可）, "bubble": "ずんだもんのひとこと（10字前後）", "post": "Xの本文（全角140字以内。1行目に結論、2〜3行で意外な中身、最後に一言で答えられる問い。リンク・ハッシュタグ・「勉強」などの学習アピールは入れない）"}
- 作ったら `python x_cards.py NNNN /tmp/x` でカードを作って見て、文字が切れていないか、画像が小さすぎないかを確かめる。

## サムネイル・タイトル（2026-11-14）
参考はゆるコンピュータ科学ラジオ、ゆる言語学ラジオ、積読チャンネル。
> 【台本づくりのスケジュールへ】スケジュールの説明に書いてある古いサムネイルの書き方（main・bubble・badge・sub）より、この節の書き方を優先する。台本には title・summary・links・thumb を scripts/long/0004.json と同じ形で書く。
> - 有名な話の例に「メタモンとミュウの体重が同じ・失敗作説」も加える（2026-11-14 プロデューサーの指摘）。
> - 字幕の書体（fonts/MPLUSRounded1c-ExtraBold.ttf）に無い漢字（中国語の「卡」など）は字幕で使わず、図で見せる。fontTools で全行を確かめる。
> - 字幕で数字と単位が別の行に分かれないようにする（L.wrap_jp で全行を確かめる）。

### タイトル
- 扇情的にする。短い言い切りに句点（「〜がある。」「〜が起きた。」）、または強い疑問（「なぜ〜のか？」）。
- ポケモンならではの話を選ぶ。昔のゲーム全般に当てはまる話（赤緑のデータ量が写真1枚より小さい、など）は使わない。
- 煽っても嘘にならない言い方にとどめ、裏取りしてから使う（例 遺伝子の改名を求めたのは任天堂ではなくポケモンのアメリカの会社なので「任天堂に消された」とは書かない）。
### サムネイル（zatsugaku_long.py の thumb()）
- 文字は左側に3行まで。小さい前置き1行と大きい2行。太い明朝体の白文字に黒い縁と影。いちばん強い言葉1つだけ赤か黄。
- 右側には話題そのものが一目でわかる画像（遺伝子ならDNAと「改名」の論文、デモなら夜の街と群衆とプラカード、地雷なら警告標識と有刺鉄線）。
- 話題と関係ないキャラ（ひまりなど）は入れない。キャラの顔の大写しで済ませない。
- 外国語の文字は使わず日本語にする（プラカードは「名前を返せ！」、標識は MINE ではなく「地雷」）。
- 背景は暗めで雰囲気のある舞台まで作り込み、左側を暗くして文字を読みやすくする。
- 絵や文字が端で切れたり重なったりしないようにする。札の文字は枠に収める。
- 前の型（紫の集中線、赤い札、白い見出し枠、ふきだし）は情報が多すぎるので使わない。
- 小さい画像を引き伸ばさない。
### 概要欄
- 1行目に動画の要約、そのすぐ下に poketango.com、続けて動画に出たポケモンごとの個別ページ（https://poketango.com/p/英語名.html）を並べる。台本の summary と links に書く。
### 台本での指定
- 台本の thumb の書き方：top（前置き）, lines（大きい2行）, accent（強調する行 0/1）, accent_color（yellow/red）, scene（demo/mine/lab）, hero（主役の画像）, placards（デモの看板）。

## 保存・報告
- 毎日作るので、ファイル名は「zatsugaku-long」のような固定の名前にせず、日付と回番号で見分けられる名前にする（例 ポケモン雑学_2026-11-14_第001回_1114-1121作成.mp4）。同じ日に何本も作ることがあるので、作成した時刻も必ず入れる。ダウンロードの名前も同じ。
- 毎日の動画はPCのチャンネル用フォルダにも保存する（許可は永続的）。ファイル名は回番号・日付・内容がわかるようにする。
- 動画で使った素材（コモンズ・ネットの画像、ポケモンの画像）も保存する。動画を作ると成果物に「…_素材」フォルダ（素材と出典.txt）が入るので、動画と一緒にPCのチャンネル用フォルダへ保存する。
- ダウンロードでプロデューサーに保存ボタンを押させない。PCのシェル（device_bash）から gh や curl で直接チャンネル用フォルダに保存する。ブラウザを使うしかないときは、Chrome の「ダウンロード前に各ファイルの保存場所を確認する」をオフにしてもらう（印をつけたスクリーンショットで頼む）。
- Chrome のタブを開くのに許可は取らない（許可は不要と言われている）。
- 古いファイル（試し版のダウンロードなど）は毎回削除する。
- PCのチャンネル用フォルダは、動画が増えたら自分で整理してよい（回ごとのフォルダに動画・サムネイル・素材をまとめる、試し版や重複の削除など）。削除も含めて任せられている。許可を取る場合も最低限の回数にまとめる。
- プロデューサーに画面操作を頼むときは、操作する場所を印をつけた画像で示す。
- 報告・途中のメッセージはすべて日本語で書く。

## これまでのミスから学んだ教訓
- 指摘された1か所だけ直さず、同じ種類のミスが動画全体（ほかの回も）にないかを探して全部直す。例 札のはみ出し、答えの先出し、言うまでもないせりふ、棒グラフ。
- 何かを直したら、関係する場所も一緒に直す。例 字幕を直したら読み上げ、図を変えたら札、ファイル名を変えたら保存の手順。
- 直したつもりで終わらせず、実際にできた動画を見て確かめてから報告する。とくに直した場面は必ず見る。
- 画面に出す画像は「その場面で視聴者が見たい物そのもの」を選ぶ。言葉や色だけで済ませない。
- せりふは視聴者の立場で読み、知らない言葉の説明がないか、返事が不自然でないか、言うまでもない確認になっていないかを見る。
- グラフや数字は、見た人が誤解しない形で出す（0からの目盛り・単位・比べる相手）。
- 報告や途中のメッセージは、英語のコードや資料を扱ったあとでも日本語で書く。
